Data model

AnimusDB is a wide-column key/value store in the Dynamo lineage: a partitioned, sorted map of maps. A table holds items; each item is addressed by a partition key and, optionally, a sort key.

  • The partition key decides where an item lives. It is hashed to a token on the table's ring.
  • The sort key orders items within a partition, which is what makes range queries inside one partition cheap.
  • Everything else is schemaless attributes — strings, numbers, binaries, booleans, nulls, lists, maps and sets.

Tables are independent. Each one has its own ring, its own tablets, and its own replication and placement decisions.

Tablets and partitioning

A tablet is a contiguous range of a table's hash ring, and it is the unit of everything: replication, placement, migration and splitting. Every key is stored under a Murmur3 token of its partition key, so a tablet owns a token range rather than a range of your raw keys.

That has a practical consequence worth knowing: scans are ordered by token, not by partition-key value. Sort-key order is preserved inside a partition, which is where ordering actually matters for queries.

Why hash the key

Range-partitioning raw keys concentrates sequential writes — timestamps, monotonic ids — onto one tablet and one leader. Hashing spreads them across the ring, so a write-heavy workload uses the whole cluster instead of one machine.

A table starts as a single tablet and splits as it grows. Tablet identifiers are never reused, and a tablet's lineage across splits is recorded so stream consumers can follow it.

Replication

Each tablet is replicated to a set of nodes — typically three — and those replicas form a Raft group. One is the leader; it serializes every write for that tablet and answers reads. A write is acknowledged once a majority of the group has it durably on disk.

Which nodes hold which replicas is a placement decision made by the control plane. The placement engine honours the replication factor, spreads replicas across failure domains, and respects residency labels — so you can require that a group's data never leaves a given region or jurisdiction.

When a node fails, the control plane notices through heartbeats, re-plans the affected tablets onto healthy nodes, and those nodes catch up by log replication or snapshot. No operator action is needed for the repair itself.

Consistency model

Single-tablet writes are linearizable: there is one leader per tablet and every write goes through its Raft log. Reads follow DynamoDB's own contract, and the choice is per request. ConsistentRead: true is linearizable — served by the leader behind a read-index barrier that confirms it is still the leader before it answers, so you never get a stale answer because you happened to hit a lagging replica. The default, ConsistentRead: false, is an eventually-consistent read: any replica answers it from its own applied state, with no barrier and no hop to the leader. It is cheaper and it scales across replicas, and it may return a slightly older — but always genuinely committed — version of the item. There is no quorum knob either way.

Multi-tablet transactions are serializable: two-phase commit across the participating tablets' Raft groups, with hybrid-logical-clock commit timestamps and MVCC snapshot reads.

A few things are deliberately not immediately consistent, matching DynamoDB's own semantics:

Item reads and writesLinearizable
Query and Scan within a tabletLinearizable
TransactWriteItems / TransactGetItemsSerializable, atomic across partitions

Availability trade-off

This is a CP system. A tablet whose replicas cannot form a majority stops accepting reads and writes for its key range rather than serving something that might be wrong. The rest of the cluster keeps working.

The two planes

AnimusDB separates cluster metadata from your data, and runs them as different systems with different scaling properties.

The control plane

One small Raft group owns the things every node must agree on: which nodes are members and where to reach them, the tablet map and its placement, and the table schema catalog. It is deliberately small and low-traffic. Its state is applied into a per-node system keyspace, so a node can restart and recover its view of the cluster from disk.

Nodes watch for metadata changes rather than polling. A single per-node reconciler reacts to the replicated state — hosting new tablets, reconfiguring groups, releasing tablets that moved away, reclaiming storage for dropped tables.

The data plane

Your data lives in one Raft group per tablet, each with its own storage engine, its own leader and its own election timers. Groups commit independently, so throughput scales with the number of tablets rather than funnelling through a single log.

An idle group quiesces: after a few seconds with no local activity it stops ticking entirely — no timers, no heartbeats, no apply polling — until a write, a peer message, or the reconciler wakes it. A cluster with many cold tablets costs proportionally little.

Any node answers

There is no routing tier and no client-side topology to configure. Every node knows the tablet map, and forwards a request it does not own to the node that does, retrying through a leader election if one is in progress.

Storage engine

Each hosted tablet gets its own log-structured merge engine: a write-ahead log for durability, memtables flushed into sorted string tables, and levelled compaction in the background. Because the engine is per-tablet, a tablet's identity is its file namespace — dropping it is deleting its files, and moving it does not disturb its neighbours.

Every byte of that engine's I/O goes through the same seam the simulator controls, which is why crash recovery is tested by injecting faults rather than by hoping.

Splits and rebalancing

Splitting

When a tablet passes its byte threshold, it splits online, in place: a single log entry mints both halves directly, already fully formed on every node that already holds the parent, so there is no separate copy, freeze or tail phase. The write pause at cutover is sub-second and masked by client retries. Both children start out on the parent's own replicas and are then moved onto their ideal placement afterward by ordinary rebalancing — the same mechanism that spreads a growing cluster.

Tablets are split-only — there is no merge operation, matching DynamoDB's own behaviour — so a table that shrinks keeps its tablet count.

Rebalancing

Replica counts across nodes converge on their own: the control-plane leader moves one replica at a time until the difference between the busiest and quietest node is at most one tablet. Adding a node is therefore all it takes to get data onto it — the same mechanism that relocates a freshly split tablet's children onto their final homes.

Indexes, streams and TTL

These three features are built on one mechanism: every tablet has a durable change log, and derived state is a consumer of it that tracks its own offset.

Secondary indexes

A local secondary index lives in the same tablet as its base item and is written atomically with it. A global secondary index is a hidden table maintained asynchronously by draining the base table's change log — which is what makes it eventually consistent, exactly as in DynamoDB.

UpdateTable adds or drops a GSI on a table that already holds data. The new index moves through a Creating → Active lifecycle while a backfill walks the existing rows, and a dropped one goes through Deleting so readers never see a half-built index.

Streams

Change data capture is served through the DynamoDB Streams API: ListStreams, DescribeStream, GetShardIterator and GetRecords. A shard is a sealed epoch of a tablet's own change log, so records are ordered per item and sequence numbers stay stable. When a tablet splits, its shards' lineage is recorded so a consumer can follow the children.

Time to live

A table can declare one attribute holding an absolute expiry time in epoch seconds. A leader-gated reaper deletes expired items through the normal write path, so index, stream and change-log maintenance all happen for free. Reads are AWS-faithful: an expired item remains visible until it is actually reaped.

API compatibility

The DynamoDB endpoint accepts DynamoDB JSON over HTTP with the usual X-Amz-Target header, so AWS SDKs work unmodified. Signature verification (SigV4) is opt-in and off by default; until it is switched on, credentials are accepted and not checked.

Transactions

A transaction that touches a single partition commits through that tablet's Raft group directly. One that spans partitions runs two-phase commit across the participating groups: the coordinator stages intents, each participant durably records its decision in its own log, and a commit timestamp from a hybrid logical clock orders the result against everything else.

Practical consequences:

  • Reads see a snapshot. MVCC versions are keyed by commit timestamp, so a transactional read observes one consistent instant.
  • Conditions are evaluated at commit. A ConditionCheck or a write action's own condition expression is checked against the committed state, giving real cross-node optimistic concurrency control.
  • A crashed coordinator does not strand data. A background resolver finishes or aborts in-doubt transactions it finds.
  • Clock skew is handled, not assumed away. Reads inside an uncertainty interval restart rather than returning a value that might be misordered.

Consoles and the admin API

Two web interfaces are compiled into the node binary, plus a JSON API underneath them.

Operator dashboard

On the admin port. Cluster and node health, the tablet map, Raft state, LSM and WAL introspection, transactions in flight, backups and restores (including per-table point-in-time recovery), and gated actions: split, flush, compact, reconfigure, drain, decommission.

Data console

On the console port. A DynamoDB-shaped app for developers: create and browse tables, inspect and edit items, review a table's configuration (including its backup and point-in-time-recovery status), and watch its stream.

The admin API

Everything the dashboard shows is plain HTTP JSON, and the animus admin subcommands are a thin client over it — usable directly from scripts:

animus admin
# observe
$ animus admin status|config|health|raft|raftkv|metrics <admin-addr>
$ animus admin peers|txns|backups|restores|control-members|storage-control <admin-addr>
$ animus admin lsm|wal <admin-addr> [tablet]
$ animus admin key <admin-addr> <key> [tablet]
$ animus admin storage-scan <admin-addr> [--tablet <id>] [--start <key>] [--limit <n>]
$ animus admin system-table <admin-addr> [--kind <kind>] [--limit <n>] [--after <cursor>]

# act
$ animus admin split <admin-addr> <tablet> <split-key>
$ animus admin flush|compact <admin-addr> <tablet>
$ animus admin reconfigure <admin-addr> <tablet> <voter,voter,...>
$ animus admin drain|drain-status|remove|decommission <admin-addr> <node-id>

# control-plane membership
$ animus admin control-add|control-remove|control-grow <leader-admin-addr> …

Deployment shapes

ShapeWhat it isCommand
CombinedEvery node runs both planes. The default, and the right choice for small and medium clusters.animusd --config … --node I
Control-onlyA small metadata quorum with no storage engine and no client endpoints.animusd control --config … --node I
Data-onlyHosts tablets and serves clients; mirrors metadata from a separate control deployment.animusd data --config … --node I
Single processA whole cluster in one process, for development and tests.animusd --cluster N

A single config file can mix combined nodes with control-only and data-only ones, so a cluster can migrate from one shape to another incrementally.

Kubernetes

An operator (the animus-operator crate) manages an AnimusCluster custom resource: one StatefulSet per cluster, a headless internal Service plus a NetworkPolicy for node-to-node traffic — Raft, forwarding, metadata mirroring, seed and join — and a separate client-facing Service for the DynamoDB edge, the only one meant to be reachable outside the cluster. Scaling a cluster is a spec edit (kubectl patch its nodes field); deleting the custom resource tears down everything it owns through ordinary Kubernetes garbage collection. A CI-gated smoke test exercises a real kind cluster end-to-end — create, bootstrap, scale, delete — on every change to this surface. The operator's own container image isn't published yet, so today it runs out-of-cluster or from a locally built image. Kubernetes' own rolling update replaces pods one at a time on an image change, but AnimusDB gives no format-compatibility guarantee between revisions, so an upgrade still means recreating the cluster in practice.

Day-two operations

Growing

A new node needs one thing: the intra-cluster address of any running node. It mints its own identity, registers with the control plane, mirrors the metadata and starts taking replicas as the rebalancer moves them.

Shrinking

drain moves a node's replicas elsewhere; drain-status reports progress; decommission removes it from membership once it is empty. A node that vanishes without draining is repaired by re-planning its tablets onto survivors.

Changing the control quorum

The control group's voters can be changed at runtime — added, removed or replaced — with control-add, control-remove and control-grow, plus leadership transfer. You do not have to rebuild the cluster to move the control plane.

Dropping a table

Dropping a table marks its tablets for reclamation; each node's reclaim loop stops the groups and deletes their storage. The process is convergent — it finishes correctly even if nodes restart partway through.

Observability

  • Metrics — a line-oriented name value text export at GET /metrics on the DynamoDB port. Counters and a leadership gauge, in stable order.
  • Tracing — optional OpenTelemetry export with W3C trace context propagated across forwarded hops, so a request that lands on the wrong node still shows as one trace.
  • Admin JSON — health, Raft state, storage internals, in-flight transactions, and the tablet map, all queryable per node.
  • Dashboard — the same data, rendered, with no external dependencies to install.

Deterministic simulation testing

This is the engineering commitment the rest of the system is built around. No component outside a single seam may read a clock, spawn a task, touch the network or disk, or generate randomness. Everything goes through that seam, which has two implementations: the real one used in production, and a simulator.

The simulator runs an entire cluster on one thread with a virtual clock, and injects:

  • network partitions, message reordering, duplication, delay and loss;
  • node crashes and restarts at arbitrary points, including mid-write;
  • disk faults and torn writes;
  • clock skew between nodes.

Every run is a pure function of its seed. A failing test prints its seed, and that seed replays exactly the same history — the same interleaving, the same crash, the same partition — on any machine.

replay
$ ANIMUS_SEED=8402173355719163220 cargo test linearizable_under_partition

Histories are checked for genuine consistency violations with Elle-style checkers rather than just checked for crashes, and corpora of seeds run in CI — a wide sweep on every push, a deep one nightly.

Why it matters to you

Distributed-systems bugs are rare interleavings. A system that can only observe them in production fixes them by guesswork. Here the interleaving is a number you can re-run — which is how splits, transactions, index backfills and stream lineage were made to hold up under faults before anyone ran them on real hardware.

Known limits

Pre-alpha means real gaps. The ones most likely to matter:

  • No TLS on any port, and no authentication beyond opt-in SigV4 on the client DynamoDB port. Every other endpoint assumes a trusted network.
  • No format compatibility between revisions. Upgrading means recreating the cluster.
  • Restore always creates a brand-new table, never in-place — matching real DynamoDB, for both on-demand backups (RestoreTableFromBackup) and continuous backups (RestoreTableToPointInTime); a source table's backup history and PITR coverage both outlive the table if it's later dropped.
  • Tablets never merge, so a table that shrinks keeps its tablet count.
  • The Kubernetes operator is new and unpublished — its own container image isn't built/published yet (run it out-of-cluster, or build the image locally), and it ships no admission webhook, so an invalid spec edit (e.g. changing controlNodes after creation) is caught by the controller after the fact, not rejected up front.
  • Not benchmarked at scale. No performance claims are made here for a reason.
