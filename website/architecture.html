Architecture

Two planes, many groups, no special node.

AnimusDB is a Dynamo-lineage store built out of ordinary Raft groups rather than a novel consensus protocol. This page is the whole shape of it: where the metadata lives, where your data lives, what a write costs, how you deploy it, and what it still can't do.

The two planes

A map, and the data the map points at.

The control plane is a single small Raft group. It holds cluster membership, the tablet map (which node owns which range of which table), and table definitions including indexes and stream configuration. It is written to when the topology changes — a node joins, a tablet splits, an index is added — and that is a rare event measured against your request rate.

The data plane is one independent Raft group per tablet. Each has its own leader, its own log and its own quorum. A write is durable and acknowledged when a quorum of that tablet's replicas has it; nothing else in the cluster is involved.

Why the split matters

Three failure modes the split removes.

Throughput

No global log

A design that orders every write through one consensus group is bounded by that group forever. Here, adding tablets adds independent groups, and the work spreads across leaders that live on different nodes.

Blast radius

No special node

There is no coordinator to lose. Losing a node costs you leader elections on the tablets it happened to lead; the rest of the cluster does not notice, and no operator action is needed to repair the replicas.

Latency

Metadata off the hot path

The control plane is consulted for topology, not for traffic. A hot control plane would put a second quorum round trip in front of every request; this one is asked when the map changes and otherwise left alone.

The trade this buys and the trade it costs. Independent groups scale and isolate well, but they don't give you free cross-tablet atomicity: anything spanning tablets needs two-phase commit, which is a real cost paid per transaction. See the consistency model.
Tablets, splits and placement

How a table becomes a set of Raft groups.

A table is a partitioned, sorted map of maps — items addressed by a partition key and an optional sort key, with schemaless attributes. Partition keys are hashed to tokens; a contiguous range of the token space is a tablet, and a tablet is the unit of replication, movement and consensus.

When a tablet grows past its threshold it splits: the range is divided and the halves continue as separate Raft groups, online. Placement is topology-aware, so replicas of one tablet are spread across failure domains rather than piled onto neighbours. Tablets also move — that is what rebalancing after a join or a drain actually is.

Two consequences worth knowing before you design your keys. First, scans are ordered by token, not by partition-key value; ordering within a partition, by sort key, is preserved as you would expect. Second, tablets never merge today, so a table that grows and then shrinks keeps the tablet count it earned at its peak.

Storage sits behind an abstraction with both an in-memory and an on-disk implementation. The in-memory one is not a toy: it is what lets an entire cluster run inside the simulator at machine speed.

The consistency model

Linearizable by default, and explicit about the exceptions.

OperationGuaranteeWhat it costs
Single-tablet writeLinearizableOne Raft round trip to a quorum of that tablet's replicas, plus a durable local write
ConsistentRead: trueLinearizableServed by the tablet's leader
ConsistentRead: falseEventually consistentCan be served without the leader; may return a stale item
Multi-tablet transactionSerializableTwo-phase commit across the participating tablets' Raft groups, with hybrid-logical-clock commit timestamps and MVCC snapshot reads
Read this as a budget, not a feature list. Every guarantee above is paid for in round trips. If an access pattern doesn't need linearizability, saying so with ConsistentRead: false is the single largest lever you have — exactly as it is on DynamoDB.
Deployment shapes

One binary, four ways to run it.

Every node is the same animusd binary. What differs is which planes it hosts, and that is a line in a config file rather than a different build. A single config can mix shapes, so a cluster can migrate from one to another incrementally instead of being rebuilt.

ShapeHostsUse it whenCommand
CombinedBoth planesThe default. Small and mid-sized clusters.animusd --config … --node I
Control-onlyMetadata quorumLarger clusters, where you want the map on dedicated, boring hardware.animusd control --config … --node I
Data-onlyTablets and client endpointsScaling capacity without growing the control quorum.animusd data --config … --node I
Single processAn entire clusterDevelopment, CI, evaluation.animusd --cluster N

Generate a starting config with animusd gen-config --nodes 3 --host 10.0.0.1. Add a node later with animusd join --seed 10.0.0.1:7105 — a new node needs exactly one thing, the intra-cluster address of any node that is already running.

Ports

Seven consecutive ports per node.

A node claims seven ports from its base port, 7100 by default. Two nodes on one host need different bases.

OffsetDefaultPurposeExposure
+07100Internal — Raft trafficCluster network only
+17101Client protocolApplication network
+27102DynamoDB HTTP endpoint — and GET /metricsApplication network
+37103Reserved—
+47104Admin API and dashboardOperator network only
+57105Intra-cluster communication — the address a joining node needsCluster network only
+67106Data consoleOperator network only
Before you point anything at it

None of these ports authenticate anyone, and none of them speak TLS, except the DynamoDB endpoint's opt-in SigV4 check. The exposure column is a description of what you must enforce yourself, at the network layer, today.

Determinism, from the inside

The whole cluster, inside one process, with time under our control.

Everything the database touches that could vary between runs — the clock, the network, the disk, thread scheduling, random numbers — goes through an environment abstraction. In production that abstraction is the operating system. In the simulator it is a deterministic stand-in: a virtual clock that advances only when the simulation says so, a message bus that decides delivery order from a seeded generator, and a storage layer that can be told to lose a write, reorder a flush, or return an error.

A whole cluster then runs inside a single process, faster than real time, with faults injected on purpose: partitions, crashes and restarts, clock skew, disk faults, message reordering and duplication.

The payoff is the seed. A failing run is described entirely by one number, so the failure replays exactly — on a colleague's laptop, in CI, a year later. That converts the expensive half of a distributed-systems bug, reproducing it, into a constant.

Day-two operations

What exists, plainly, and what doesn't.

Available

  • Growing — a joining node needs the intra-cluster address of any running node; tablets rebalance onto it online.
  • Shrinking — drain relocates a node's replicas, drain-status reports progress, decommission removes it.
  • Node failure — replicas are re-created automatically; no operator action.
  • Control-plane membership — voters can be changed at runtime without rebuilding the cluster.
  • Dropping a table — tablets are marked for reclamation and each node's reclaim loop stops the groups and deletes the storage.
  • Backup and restore — on-demand backups and continuous backups (point-in-time recovery to any second); both outlive a dropped source table and restore into a brand-new one.
  • Metrics — a line-oriented name value export at GET /metrics on the DynamoDB port: counters and leadership gauges.
  • Tracing — optional OpenTelemetry export with W3C trace-context propagation.
  • Introspection — admin JSON endpoints for health, Raft state, storage internals, in-flight transactions and the tablet map, per node, plus a dashboard that renders them with no external dependencies.

Missing

  • Upgrades — on-disk formats change between revisions, so upgrading means recreating the cluster and reloading the data.
  • TLS — absent on every port. Authentication — opt-in SigV4 on the client DynamoDB port only; every other port is unauthenticated.
  • Alerting rules — metrics are exported, but no reference dashboards or alert definitions ship with them.
Those gaps are, together, the reason the status page says pre-alpha rather than beta. They are ordinary engineering, not open research questions, and they are what the roadmap is pointed at.
Known limits

The list we'd want to be shown.

  • No TLS on any port, and no authentication beyond opt-in SigV4 on the client DynamoDB port.
  • No format compatibility between revisions. Upgrading means recreating the cluster.
  • Restore always creates a brand-new table, never in-place.
  • Tablets never merge, so a table that shrinks keeps its tablet count.
  • Not benchmarked at scale, and no performance claims are made for that reason.
  • No production use by anyone, including us.
