A masterless NoSQL database that speaks DynamoDB.

AnimusDB is a horizontally scalable database you run yourself. It serves the DynamoDB and Cassandra CQL wire protocols, keeps every read and write linearizable instead of eventually consistent, and its distributed core is verified by deterministic simulation testing.

What it does

The DynamoDB feature set, on infrastructure you control.

AnimusDB implements the parts of DynamoDB applications actually depend on — not just get and put — and runs them on a cluster you own, in a region you choose.

Your existing code

Point the AWS SDK, aws CLI, or any DynamoDB client at a node's endpoint. Tables, items, expressions, conditional writes and paginated queries all work the way your application already expects.

Strong consistency

Every partition is its own Raft group with a single leader. Reads and writes are linearizable by default — no quorum tuning, no read repair, no "eventually".

Transactions

TransactWriteItems and TransactGetItems commit atomically across partitions — two-phase commit over the per-partition Raft groups, with hybrid-logical-clock timestamps and MVCC snapshot reads.

Secondary indexes

Global and local secondary indexes, maintained from each partition's durable change log. UpdateTable adds or drops a GSI on a table that already holds data, backfilled online.

Streams

Change data capture through the DynamoDB Streams API: shard iterators, per-item ordering, and stable sequence numbers your existing consumers can read.

Time to live

Declare a TTL attribute and a background reaper expires items for you — deleting through the same write path, so indexes and streams stay correct.

Automatic sharding

Data is partitioned into tablets on a hash ring. A tablet that grows past a byte threshold splits in the background; replicas rebalance across nodes on their own.

Data residency

Nodes carry topology labels. Placement policy spreads replicas across failure domains and can pin a group's data to a chosen region or jurisdiction.

Consoles included

Two web UIs ship in the binary: an operator dashboard for cluster health, Raft and storage internals, and a data console for browsing and editing tables.

How it works

Two planes, never blurred.

A small Raft control plane owns cluster metadata. The data plane is one Raft group per tablet, each with its own storage engine. Nodes are interchangeable — there is no special master to lose.

Why the split matters

Cluster metadata — who is a member, which tablet owns which key range, what tables exist — is small, changes rarely, and must never diverge. It lives in one Raft group.

Your data is large, changes constantly, and must scale. It lives in as many Raft groups as you have tablets, each replicated and led independently, so throughput grows with the cluster instead of funnelling through one log.

What that buys you

  • No hot log. Every tablet commits in parallel; adding nodes adds capacity.
  • Failures are local. Losing a node costs those tablets an election, not the cluster.
  • Idle costs nothing. A tablet with no traffic quiesces — its timers and heartbeats stop until something touches it.
  • Growth is online. New nodes join from a seed address and are handed tablets automatically.
a failure, replayed exactly
# a simulation test fails and prints its seed
$ cargo test -p animus-cp-data

  read observed a stale value (seed = 8402173355719163220)

# replay that exact history — same partitions, same
# crashes, same message interleaving, every time
$ ANIMUS_SEED=8402173355719163220 \
    cargo test linearizable_under_partition
Correctness

Every bug is reproducible from one number.

AnimusDB has no wall clock, no raw threads, no real sockets and no unseeded randomness in its logic. Time, scheduling, the network and the disk all flow through a single seam, so the entire cluster can be run inside a deterministic simulator that injects partitions, crashes, clock skew and disk faults.

Distributed bugs that would be one-in-ten-thousand flakes in production are found in the simulator and replayed byte-for-byte from their seed. Histories are checked for real consistency violations with Elle-style checkers, not just for "did it crash".

Deployment

Run it the shape your cluster needs.

The same binary covers a laptop, a handful of machines, and a Kubernetes-managed fleet.

Combined nodes

Every node runs both roles — control and data. The simplest shape, and the one to start with: animusd --config cluster.json --node 0.

default

Split control & data

Run a small, stable control quorum on their own machines with animusd control, and scale storage independently with animusd data.

large clusters

Kubernetes

Client ports and intra-cluster ports are separate listeners, so node-to-node traffic stays inside the cluster while only the DynamoDB and CQL edges are exposed.

operator: planned
Scaling out

Adding a node is one command — it registers itself, mirrors cluster metadata, and the placement engine starts moving tablet replicas onto it until the cluster is balanced. Removing one is drain then decommission; replicas leave before the node does.

Status

Honest about where this is.

AnimusDB is pre-alpha. The distributed core is real and tested hard — replication, sharding, splits, rebalancing, transactions, indexes, streams and TTL all work — but the project has not been run in production by anyone, and there are no compatibility guarantees between revisions yet.

Before you point anything at it

There is no authentication on any port today. Every endpoint — client, admin, and both consoles — assumes a trusted network. Do not expose a node to the public internet, and do not store data you cannot afford to lose or recreate.

On-disk and wire formats change without migration paths; assume a cluster is recreated from scratch between revisions. If that's a fit for what you want to do — experiment, benchmark, contribute — it's a good time to get involved.
