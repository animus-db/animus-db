Why this exists

The API is the standard. The hosting doesn't have to be.

DynamoDB's API won for good reasons: predictable latency at any size, a data model that survives scale, and an SDK in every language your teams already use.

But there is one place to run it. One vendor sets your price, your regions and your recovery time — and revisits all three on their schedule, not yours.

A dependency on those terms would normally go out to tender. This one doesn't, because leaving means rewriting every access pattern you have. The switching cost is what removes the option, and it grows every quarter you don't exercise it.

AnimusDB removes the rewrite. Keep the API; change who runs the cluster underneath.

Who it's for

Three situations where this matters.

Migration

Leaving AWS

Compute and object storage port in weeks. A decade of accumulated DynamoDB access patterns doesn't — which is why the data layer is usually the thing that blocks the move. It stops being the thing that blocks the move.

Regulation

Residency requirements

Pin a dataset to a jurisdiction because the regulator says so, not because a region happens to exist there. The cluster runs where you put it, under the law that applies where you put it, on hardware whose owner you can name.

Environment

On-prem and edge

Factory floor, ship, forward site, private cloud. Runs where there is no managed anything — and keeps running when the link back to head office doesn't.

And one situation where it doesn't. If you are happy on DynamoDB, committed to AWS, and expect to be in five years, AnimusDB is not an upgrade. Nothing here beats a managed service on operational burden, and we are not going to pretend otherwise.
Trust

Bugs found before you meet them.

AnimusDB runs its whole cluster inside a deterministic simulator. Network partitions, node crashes, clock skew, disk faults and message reordering are injected on purpose, thousands of times over, at machine speed. The one-in-ten-thousand interleavings that surface at 3am in production surface here instead.

Every run is driven by a single number. Give the simulator the same seed and it reproduces the same failure, step for step — so a fix is verifiable rather than hopeful, and the run that caught the bug becomes the run that keeps it caught.

What it does not do is prove correctness. It exercises the faults we thought to model, on the components we put under it. That is a large claim and a bounded one, and the article below draws the boundary rather than blurring it.

How it works

Two planes, never blurred.

A small Raft group holds cluster metadata: membership, which node owns which tablet, what tables exist. It is consulted when the topology changes — not on the path of your reads and writes.

Your data lives in as many independent Raft groups as you have tablets, each replicated and led separately. A write is acknowledged once a quorum of that tablet's replicas holds it. Nothing funnels through a single log, and no node is special. Lose one and you lose an election on some tablets, not the cluster.

Where it stands

Pre-alpha. Here's the honest version.

Works today

  • Per-tablet Raft replication, linearizable writes
  • Tablet splits, movement and online rebalancing
  • Multi-tablet transactions (2PC, MVCC snapshot reads)
  • Secondary indexes, added and dropped online with backfill
  • Streams and time to live
  • On-demand backup and restore, plus continuous backups (point-in-time recovery) to any second
  • Metrics endpoint, admin API and a built-in dashboard
  • Growing a cluster by seed address; drain and decommission to shrink one

Planned

  • TLS on every port; authentication beyond the client port's opt-in SigV4
  • On-disk format stability, then rolling upgrades
  • A Kubernetes operator
  • Published benchmarks with disclosed methodology

Not yet

  • Production use, by anyone, anywhere
  • Any performance claim — it has not been benchmarked at scale
  • Compatibility between revisions: upgrading means recreating the cluster
  • Tablet merging — a table that shrinks keeps its tablet count
Before you point anything at it

There is no TLS today, and no authentication beyond opt-in SigV4 on the client DynamoDB port. Every port assumes a trusted network. Don't put this on the public internet, and don't store data you can't recreate.
