Compatibility

It speaks DynamoDB, so your SDK doesn't know the difference.

the entire integrationdiff
- endpoint: dynamodb.eu-west-1.amazonaws.com
+ endpoint: animus.internal:7102

Tables of items addressed by a partition key and an optional sort key, with schemaless attributes — the model you already design for. Working today: PutItem, GetItem, UpdateItem, DeleteItem with condition and update expressions; Query and Scan with filters, pagination and index queries; the batch operations; transactions; secondary indexes added and dropped online with backfill; streams; TTL.

Four differences worth knowing before you assume a drop-in: scans are ordered by token rather than partition-key value; there is no capacity metering, so no RCUs and no throttling responses; credentials are verified only when the opt-in SigV4 check is switched on — by default any caller that can reach the port is trusted; and the AWS-side integrations — Lambda triggers, PITR, DAX, CloudWatch — have no equivalent.

Architecture

Two planes, one Raft group per tablet, no special node.

A small Raft group holds cluster metadata: membership, which node owns which tablet, what tables exist. It is written to when the topology changes, which is rare against your request rate, and it is not on the path of your reads and writes.

Your data lives in as many independent Raft groups as you have tablets, each replicated and led separately. A tablet is a contiguous range of the token space, and it is the unit of replication, movement and consensus. When one grows past its threshold it splits, online, into two groups.

Nothing funnels through a single log and no node is special — so losing one costs you an election on the tablets it led, not the cluster.

The write path, the quorum acknowledgement, and the control plane held off the request path. This is the full version; the Architecture page reuses it.

Testing

The cluster runs inside a deterministic simulator.

Everything that could vary between runs — the clock, the network, the disk, scheduling, random numbers — goes through an abstraction. In production that is the operating system; under test it is a deterministic stand-in, so a whole cluster runs in one process, faster than real time, with partitions, crashes, clock skew and disk faults injected on purpose.

Because nothing varies except the seed, a failing run is described by a single number and replays exactly. That turns the expensive half of a distributed-systems bug — reproducing it — into a constant.

It is not a proof, and it only covers the faults that were modelled. The article below draws that boundary properly, and gives you six questions to interrogate anyone making this claim, us included.

Performance

No benchmarks yet — but the cost model is knowable.

AnimusDB has not been benchmarked at scale, so it makes no performance claims. Publishing a number today would measure an unfinished storage path and then be quoted back at us for years.

What the architecture does fix is the shape of the cost. A write is one Raft round trip to a quorum plus a durable local write, so it cannot be acknowledged before the network has carried it to that quorum — put replicas in three availability zones and your write floor is a metro round trip. A linearizable read is served by the tablet leader; an eventually-consistent one need not be. A transaction across tablets is two-phase commit, and costs accordingly.

Throughput scales with tablet count, because tablets are independent groups with independent leaders. It does not scale within one tablet, and a hot partition key is still a hot partition key — exactly as on DynamoDB.

Operating

One binary, four shapes, seven ports.

Every node is the same animusd binary; what differs is which planes it hosts, and that is a line in a config file. Run combined nodes by default, split into control-only and data-only as a cluster grows, or start an entire cluster in a single process for development. A config can mix shapes, so a cluster migrates between them incrementally rather than being rebuilt.

A node claims seven consecutive ports from its base, 7100 by default: Raft traffic, the client protocol, the DynamoDB HTTP endpoint (which also serves GET /metrics), the admin API and dashboard, intra-cluster communication and a data console.

Day two, available

  • Growing: a joining node needs the intra-cluster address of any running node
  • Shrinking: drain, drain-status, decommission
  • Node failure: replicas re-created automatically, no operator action
  • Metrics, OpenTelemetry tracing, admin JSON endpoints and a built-in dashboard

Day two, missing

  • Backup and restore — no tooling exists
  • Upgrades — formats change between revisions, so upgrading means recreating the cluster
  • TLS — absent on every port; authentication — opt-in SigV4 on the client port only
Every port assumes a trusted network

Nothing speaks TLS today, and only the client DynamoDB port can verify a signature — opt-in, off by default. Don't put this on the public internet, and don't store data you can't recreate.

Licensing

AGPL-3.0, and what it asks of you.

Your application talks to AnimusDB over the DynamoDB HTTP API using AWS's own SDKs. It links nothing of ours, and using a database over a network protocol does not put your application under that database's licence.

Run an unmodified build, however commercially, and you owe no one any source. The obligations begin when you modify AnimusDB and let people interact with your modified version over a network — that is section 13, and it is the clause that makes this AGPL rather than GPL.

There is no commercial licence on offer today. The contributor agreement keeps one possible, which is a different thing from promising one.
